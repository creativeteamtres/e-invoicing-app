## Not ready for real customer operations

- The seller profile and buyer in this run are fictional QA data. Replace them with accurate registered business and recipient information before issuing a real invoice.
- SMTP is unconfigured; no email was sent. Add the user’s own provider details and encrypted credential key before enabling delivery.
- Mustang is installed, but a complete ZUGFeRD PDF/A-3 generation/validation run was not performed; that flow also requires a real PDF visual source.
- Peppol and API/EDI access-point adapters are not implemented in this build. The panel says so rather than offering dummy credential fields.
- Stripe is unconfigured. No checkout/payment was attempted.
- The DATEV file was generated with example mappings solely to test the workflow; have the customer’s tax advisor verify real mappings.
- SQL append-only routes, digests, and a hash-chained audit log are not immutable WORM storage and do not establish GoBD compliance. Production needs an appropriate archive/storage design and deployment review.
- The integration panel edits business profile and SMTP at workspace level, DATEV mappings per export, and reports host-level services. KoSIT/Mustang/Stripe, database, and retention configuration stay in one server deployment `.env`; that is intentionally not editable from a normal browser session because it contains system secrets. See `backend/README.md`.

All generated test artifacts, customer data, and exports were kept in the isolated QA database. Nothing was sent to an external recipient or Peppol network.
